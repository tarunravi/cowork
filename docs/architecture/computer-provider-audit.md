## Reference C: Rakazo

### Provider contract and computer ownership

**Implemented.** [`packages/adapter-kit/src/interfaces.ts:92–202`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapter-kit/src/interfaces.ts#L92) defines `SandboxProvider`: describe capabilities; provision/reconnect; separate idempotent `prepare`; streamed command execution; screen connection; observation and batched actions; leased human input; file listing/read/write; workspace export/import; snapshot; stop/destroy. Optional hooks cover page-browser tools, terminals, run cancellation, background-work inspection, keepalive, and screen release. This is a machine adapter, separate from `AgentRuntime`, `JobPublisher`, and `AgentHomeStore` in the same file. Separating `provision` from `prepare` lets the lifecycle capture a machine reference before later setup can fail.

**Implemented.** [`packages/db/src/computers.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/db/src/computers.ts#L13) keys Team computers by `team:<spaceId>` and Private (`dedicated`) computers by `bot:<botId>`, with corresponding durable home keys. Quota checks serialize creation per user with a PostgreSQL advisory transaction lock. [`computer-lifecycle.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/computer-lifecycle.ts#L163) uses persisted state and compare-and-swap claims around provisioning, checking maintenance reservations, provider kind/reference, and claim timestamps before activating a machine.

**Documented.** [`docs/computer-runtime.md`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/docs/computer-runtime.md#L15) describes Team bots starting in `bots/<bot-id>/` with deliberate collaboration under `shared/`; a Private computer uses the entire home. Team directories are organizational, not access-control boundaries. Bots share the OS account, shell, workspace, and X11 access. Private computers are the stronger boundary when tasks cannot trust each other.

**Unverified.** No live provider provisioning, tenant escape test, quota race, or provider credential policy was exercised. The presence of Docker/E2B/Daytona/CreateOS/Boat/Railway adapters does not establish identical capabilities or isolation across them. The source inventory includes [`sandbox-factory.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/sandbox-factory.ts), but this was not an exhaustive audit of each vendor API.

### Chromium persistence, desktop provisioning, and streaming

**Implemented.** [`packages/core/src/node/desktop-runtime.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/core/src/node/desktop-runtime.ts#L86) derives `.browser-profiles/chromium-bot-<key>` from stable screen/bot identity, separately from the allocated display slot. The launcher sets a distinct `--user-data-dir` and loopback debugger port. It uses `--password-store=basic` and `--no-sandbox`: profile files contain sensitive login state, and the surrounding computer must supply the security boundary. Browser shutdown attempts `Browser.close` before termination so profile databases can flush.

**Implemented.** [`packages/adapters/src/linux-desktop.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/linux-desktop.ts#L44) factors common Linux desktop operations over provider-supplied command execution, environment paths, and protected port URLs. It passes screen identity and lease identity into desktop allocation and control. [`infra/sandboxes/supervisor/src/supervisor-logic.ts:208–278`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/infra/sandboxes/supervisor/src/supervisor-logic.ts#L208) allocates display slots, rejects older owners, marks a release in progress, and frees a slot only after release completes; warm release can retain the screen as idle instead.

**Documented.** The [runtime guide](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/docs/computer-runtime.md#L19) describes per-bot X displays and Chromium processes, lazy desktop startup, distinct revocable view/control capabilities, and a common screen gateway with unique Unix-socket targets. Failed teardown keeps a slot reserved. Docker successful runs may retain the browser and viewer while revoking run control; configured screen limits can evict idle screens. This is desktop coordination inside one trusted computer, not a separate VM per bot.

**Source conflict.** [`VISION.md`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/VISION.md#L32) describes canonical/shared Team browser identity. Current runtime documentation and the profile-path implementation instead specify independent per-bot profiles. Do not design OpenBot around shared cookies or profile merging on the strength of the vision document.

**Unverified.** No desktop, browser, gateway, or video session was started. The guide's capacity statement about 100+ saved profiles is not a measured concurrent-desktop limit. No FPS, latency, memory, or display-isolation benchmark was run. Source includes an opt-in [Docker Team desktop regression](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/infra/sandboxes/supervisor/src/team-desktops.docker.test.ts); its existence is not evidence that it passed here. Browser profiles separate normal browser state, but a Team bot with shell access can still read another bot's profile.

### Storage and recovery

**Implemented.** [`packages/adapters/src/home.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/home.ts#L18) implements `LocalAgentHomeStore` with serialized in-process writes, staged copies, rename/swap, previous-copy recovery, and revision metadata. It explicitly advertises `revisions: false`; `restore` does not select an immutable historical revision. [`computer-workspace.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/computer-workspace.ts#L280) exports remote files into staging before committing, while Docker with a local home store advances a revision marker because the home is already mounted. Remote Team checkpoints check peer execution/control ownership before saving; portable-file filtering excludes transient browser state only under `.browser-profiles`.

**Documented.** The [persistence section](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/docs/computer-runtime.md#L86) makes the portable home the recovery boundary. Replacement machines import it; remote exports quiesce browsers. A disposable OS image is separate: packages installed outside the home do not migrate. The operator must persist, encrypt, and back up `DATA_DIR`; an opaque provider reference is an optimization, not the durable source of files.

**Implemented.** [`computer-update.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/computer-update.ts#L55) reserves a computer in a transaction before update/recovery, excluding active execution, mode changes, and control. `performComputerUpdate` claims only `queued` operations, preventing destructive replay on job redelivery. The reconciler marks a stale running operation interrupted after ten minutes but retains its reservation because a missing heartbeat does not prove provider calls stopped. The [maintenance guide](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/docs/computer-runtime.md#L119) documents the operator-only release procedure after workers/provider operations are confirmed stopped.

**Unverified.** Latest-home storage is not point-in-time backup, cross-process writer serialization, or an object-store implementation. No crash, disk-full, interrupted rename, browser SQLite consistency, remote replacement, or restore test was executed. Recovery may lose changes since the last completed checkpoint.

### Routines, delegation, fencing, and uncertain side effects

**Implemented.** [`wakeup.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/wakeup.ts#L19) supplies Graphile Worker job publication and execution over PostgreSQL, with job keys, scheduled times, and attempt limits. [`background-job-handlers.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/background-job-handlers.ts#L58) routes run continuation, routine wake/retry, maintenance, idle sleep, and control expiry. [`job-reconciler.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/job-reconciler.ts#L101) uses advisory-lock leadership to revisit queued/expired runs and due routines. [`executor.ts`, `wakeRoutine`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/executor.ts#L3165) checks that the routine remains active and its scheduled timestamp still matches before dispatch.

**Implemented, two distinct lifetimes.** [`bot-messages.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/bot-messages.ts#L65) records peer-bot messages, target runs, and events transactionally, with delivery-key deduplication and return routing. [`child-bots.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/child-bots.ts#L51) creates lasting bots with parent/spawn identity and their own thread/run. By contrast, [`pi-runtime.ts`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/pi-runtime.ts#L1361) implements `run_subagent` in the parent runtime: no further nesting, a four-helper parallel gate, and abort propagation to nested agents. These helpers are not independent crash-recoverable application tasks.

**Implemented.** [`computer-lifecycle.ts:582–710`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/packages/adapters/src/computer-lifecycle.ts#L582) acquires Team execution leases per computer/bot/run, increments a monotonic fence on reacquisition, conditions renewals on owner/fence/unexpired lease, and retains expired rows as fencing tombstones. The [supervisor](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/infra/sandboxes/supervisor/src/supervisor-logic.ts#L208) checks screen ownership before slot reuse. These are coordination guards, not barriers against arbitrary processes already running under the shared OS account.

**Implemented.** [`supervisor-logic.ts:105–152`](https://github.com/elie222/rakazo/blob/e6abd1cfb58e8bc77ce882fef430c15e6251ec83/infra/sandboxes/supervisor/src/supervisor-logic.ts#L105) distinguishes pre-connect control failure from a request that may have partially applied actions. Only the former permits automatic action fallback/replay. A timeout or connection reset after dispatch is not proof that a click or command did nothing.

**Unverified.** This audit does not establish exactly-once side effects, universal provider fencing, or lossless parent/child recovery. Durable rows plus retries require idempotency and reconciliation at each external-effect boundary. Do not infer native-helper survival from durable peer-bot messaging.

Without required gVisor it can fall back to `runc`; `ContainerConfig` defaults include `prefer_gvisor: true`, `require_gvisor: false`, and `allow_install_runsc: false`. [`container/gvisor.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/crates/cua-vmm/src/container/gvisor.rs) contains provisioning plans for native Linux/Colima and explains why Docker Desktop's VM is not automatically provisionable. ### Existing-machine attach, files, and screen I/O

**Implemented.** [`sandbox.rs`, `connect_ref` and `spacesd`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/crates/cua-sandbox-core/src/sandbox.rs#L1344) supports direct address attachment separately from local state-backed reconnection. Attachment probes spacesd capabilities and reports `SpacesdNotAvailable` when absent. The [Spaces API](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/crates/cua-spaces/README.md#L29) documents `spaces.add(url, token, name)` and relay-machine discovery. Direct attach reuses an existing OS/account; it does not add isolation. `cua host setup` and account relay access are documented, not exercised here.

**Implemented.** [`cua-spacesd-client/src/fs.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/crates/cua-spacesd-client/src/fs.rs) implements chunked, SHA-256-verified resumable transfers, with a native streaming upload and a gRPC-Web begin/chunk/commit fallback. [`cua-spacesd-server/src/filesystem/mod.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua-spacesd/crates/cua-spacesd-server/src/filesystem/mod.rs) contains the server implementation. General filesystem operations are distinct from the documented Downloads-confined `send_file` flow. Neither is an OpenBot artifact retention or backup policy.

**Implemented.** [`grpc/computer.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua-spacesd/crates/cua-spacesd-desktop/src/grpc/computer.rs) implements screenshots, display/window targeting, pointer, keyboard, and clipboard. It checks screenshot identity/geometry and rejects stale screenshot-based coordinates rather than applying them to resized targets; it also checks window input ownership. The [computer protobuf](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/proto/cua/env/v1/computer.proto) declares the transport contract. Action support depends on the reported capability and desktop session, not merely the OS name.

**Implemented security boundary.** [`auth.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua-spacesd/crates/cua-spacesd-server/src/auth.rs) and [server documentation](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua-spacesd/crates/cua-spacesd-server/README.md#L23) define authenticated RPC access, token-derived tickets, and token rotation/revocation. Tokenless default binding is loopback; non-loopback requires authentication or an explicit restricted bootstrap mode. Health is unauthenticated. Extensions must authenticate their own HTTP/media routes. None of these capabilities replaces OpenBot's user authorization, approvals, or audit history.

### Streaming, video, concurrency, and persistence

**Implemented.** [`grpc/stream.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua-spacesd/crates/cua-spacesd-desktop/src/grpc/stream.rs) enumerates targets, negotiates media, mints session tickets, requests keyframes, and closes sessions. [`cua-spacesd-session/src/lib.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua-spacesd/crates/cua-spacesd-session/src/lib.rs) uses bounded subscriber mailboxes, ordered publication, and asynchronous encoders that can drop obsolete frames. This is flow control for live viewers, not durable execution/event delivery.

**Documented.** [spacesd](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua-spacesd/README.md) and [media wire documentation](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/proto/MEDIA.md) describe H.264 video, Opus audio, WebSocket `/media`, and optional QUIC. Native capture/encoding is platform-specific: X11/Hyprland paths on Linux, ScreenCaptureKit/VideoToolbox on macOS, Windows.Graphics.Capture/OpenH264 on Windows. Hardware encoder discovery does not establish active NVENC/VA-API/QSV/AMF support. Streaming support also does not establish a durable MP4 recording API, artifact retention, or an OpenBot video player; those were not verified.

**Implemented limitation.** [`cua-spaces/src/stream.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/crates/cua-spaces/src/stream.rs#L9) defines a client seam, but `stream_session` needs a registered streaming implementation; the supplied implementation is [`cua-spaces-ext/src/stream.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/crates/cua-spaces-ext/src/stream.rs), under FSL. MIT API availability is not evidence that a plain SDK build includes the Spaces viewer/decoder stack.

**Concurrency.** Driver's [session implementation](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua-driver/rust/crates/cua-driver-core/src/session.rs) provides per-session ownership/cleanup; spacesd separates human input attribution and window leases. These mechanisms can coordinate multiple viewers/agents but do not create separate filesystems, browser identities, OS users, or safe concurrent writes to one Chromium profile. For OpenBot, use one isolated computer/profile per private ownership scope, or add an explicit trusted Team-computer scheduler and per-bot profiles. No maximum concurrent session/desktop count or throughput was established.

**Persistence and recovery, implemented in part.** [`state.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/crates/cua-sandbox-core/src/state.rs) persists named sandbox metadata through private temporary-file writes/rename and records ephemeral owner leases for later cleanup. [`container/mod.rs`](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/cua/crates/cua-vmm/src/container/mod.rs#L1188) implements container filesystem checkpoints using commit or export/import; these are not proof of guest RAM/process recovery or application-consistent browser snapshots. Reconnecting a machine does not resume an OpenBot task. Cua Volume and persistent-agent extensions have separate FSL implementations; this audit did not inspect their full recovery model or any user's local state. No backup, reboot, suspend/resume, reconnect, or multi-process recovery scenario was run.

**Browser-persistence limit.** The [Linux image Dockerfile](https://github.com/trycua/cua/blob/864fd4e525fe14d55fda25502c69132505a0e85d/libs/images/linux/Dockerfile#L114) describes `browser_prepare` launching Chromium with a Driver-owned throwaway profile. A persistent sandbox disk therefore does not, by itself, promise reusable browser login identity. OpenBot must explicitly own the stable profile path, its exclusive writer, flush/checkpoint policy, and reset semantics; Driver's default browser preparation is not a substitute for that contract.

## Integrating with OpenBot without a second backend

1. **Extend the existing seam.** `server/src/computer/provider.ts` already selects Docker supervisor, shared, or Kubernetes Sandbox implementations and exposes lifecycle/status plus session identity. Keep that application-facing boundary. Add explicit capabilities and an opaque provider reference rather than adopting Rakazo's Prisma/API/Pi/Graphile stack or Cua's Spaces application. Where OpenBot actions currently speak its HTTP computer protocol, a Cua lifecycle adapter alone is insufficient: add a small protocol translator at `server/src/computer/client.ts` / `agent-computer`, or run the existing computer service inside the SDK-provisioned machine.
2. **Keep current persistence and ownership.** OpenBot's `agent-computer/src/profiles.ts` already uses persistent browser contexts; `server/src/computer/sandbox.ts` distinguishes suspend (keep volumes) from reset/delete. Keep OpenBot's PostgreSQL queue (`server/src/work/queue.ts`), thread leases (`toolkit/src/run-turn.ts`), routines (`server/src/routines/`), and approvals (`server/src/approvals/`). Add durable run/attempt/child relationships where missing, as [decisions.md](decisions.md) proposes. Cua daemon state or provider IDs must not become a second task database.
3. **Start with Private computers.** Retain OpenBot's per-bot computer model. Its shared fallback explicitly shares the browser; it is not Rakazo Team mode. If Team mode is required, add a durable team-computer identity, separate bot profile/display identity, execution fences, revocable view/control grants, and computer-wide maintenance/checkpoint exclusion. Never run concurrent Chromium writers against one profile. Revalidate stale snapshots after computer replacement; OpenBot's optional `sessionOf` can return unknown, so it is not a complete fail-closed mutation fence.
4. **Adopt recovery rules before breadth.** Use monotonic attempt/computer generations checked at the action gateway, owner-conditioned renew/finish, non-reusable screen grants, and a reserved/interrupted maintenance state. Expired leases must not authorize a second destructive provider call while the first may still execute. On uncertain click/command outcomes, observe/reconcile before retrying. Choose an OpenBot-owned portable-home/checkpoint policy and backups; do not add Cua Volume as another canonical store.
5. **Make Cua optional and capability-gated.** The MIT SDK can supply lifecycle for local Linux containers/VMs, while MIT Driver can supply native control where supported. Prefer explicit gVisor requirements for untrusted Linux workloads; fail clearly if the engine cannot meet them. Keep OpenBot's existing browser screencast (`agent-computer/src/screencast.ts`, JPEG over WebSocket) for the first integration. Full desktop streaming is a distinct adapter and licensing decision; spacesd can be a machine-side service if its terms fit, but OpenBot remains the sole control plane for runs, scheduling, permissions, and artifacts.
