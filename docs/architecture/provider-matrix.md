## Legend

Availability (a harness is registered or has a Dockerfile) is not the same as a feature being implemented. Each cell below states which one it is.

- **Impl**: the repo's own adapter code does this. Cited paths are evidence.
- **Partial**: some of it is implemented, with a stated gap.
- **Delegated**: the adapter hands this to a pinned bridge or framework. The repo does not verify the behaviour per capability.
- **Unverified**: no repo code or test shows it. Do not assume it.
- **Unsupported**: the repo states it is not provided.
- **Not used**: the framework could do it, but the adapter does not configure it.

## Notes on rows

- **Codex, sessions and events.** `agent-codex/src/adapter.ts` saves session IDs atomically and resumes them through `codex exec resume`. Only completed `agent_message` items produce assistant text; command and file-change items are not forwarded. Session/event tests use `tests/fake-codex.ts`, so they do not establish real CLI turn behavior. A separate test starts the pinned local Responses proxy with a synthetic key to check rejection of non-Responses endpoints; that does not test Linux sandbox isolation.
- **Codex, packaged source.** `agent-codex/Dockerfile` pins the CLI through `package.json`/`bun.lock`, runs the adapter as `bun`, and stores CLI state and workspaces in one volume. `.github/published-images.json` includes `agent-codex`; `docker-compose.yml` selects the image and starts a separate proxy with the key secret. A local `linux/arm64` build from these files succeeded and `codex --version` ran. They do not prove a published image or a working packaged runtime.
- **Codex, service-token lifetime.** Compose supplies `MANAGED_AGENT_TOKEN` to the adapter at process startup. The Dockerfile starts Bun directly. `src/index.ts` captures the token in memory and deletes its JavaScript environment entry before constructing the adapter. `parentEnvironment` allowlists the CLI/probe environment, excluding service tokens. Deleting a JavaScript environment entry does not establish erasure of the initial Linux process environment: if it remains readable through `/proc/<adapter-pid>/environ`, it could expose the startup token to a shell with that access.
- **Codex, fail-closed probe and remaining gaps.** Before each turn, `adapter.ts` runs `codex sandbox` with workspace-write and network disabled. Its shell scans readable `/proc/*/environ` for credential variable names, attempts HTTP to the resolved adapter port (4215 by default) and proxy port 60001, and checks workspace writes. A visible retained startup token causes this probe to reject the turn, which may make the packaged adapter unusable. Read errors are skipped; passing this probe is not proof that initial environment bytes were erased or all process-read paths are blocked. No packaged run establishes the actual `/proc` visibility or Linux sandbox behavior. The proxy has a separate key mount and PID namespace but shares the adapter's network namespace. Whether the sandboxed shell can reach the credentialed proxy on port 60001 remains unresolved; the probe's port-60001 check has not been exercised at runtime.
- **Claude SDK, main-mode tools.** `build_options` sets `options.tools = []` only when `model_only` is true (`adapter.py` line 97). Upstream `build_options` (`agent-claude-sdk/.venv/lib/python3.13/site-packages/ag_ui_claude_sdk/adapter.py` around line 477) adds `allowed_tools` only for ag-ui tools. So built-in tool availability in main mode comes from SDK defaults and was not run here.
- **LangGraph, ChatGPT path.** `agent-langgraph-agui/src/main.py` (around line 137) can run a model through a ChatGPT sign-in auth file rather than an API key. The repo has tests for this (`tests/test_tool_protocol.py` around line 564 and the provider-boundary tests).
- **Mastra.** `webCreate: false` (`shared/harnesses.json`) means the web create API cannot make this row work. The server reaches it through `@ag-ui/mastra` (`server/src/copilot.ts` around line 1129).

## Implications for the first vertical slice

Factual only. These do not commit the slice to anything.

- **Interruption is not uniform.** Repo code implements interruption in `agent-claude-sdk` and `agent-codex` (working tree), and partly in `agent-langgraph-agui`. The other rows rely on framework or bridge behaviour the repo does not check. Assuming one stop behaviour across harnesses would not match the code.
- **Event fidelity differs.** Codex emits whole assistant messages and no tool events. LangGraph and Claude SDK emit tool events. The remaining Python rows delegate event shape to bridges, and the repo tests do not check it (Langroid's `tests/test_tools.py` is the exception).
- **Computer access is not an adapter capability in any row.** The repo's pattern is surface-executed tool calls (LangGraph's `tool_runtime.py`, Claude SDK's `mcp__ag_ui__*` client tools). Computer use is a surface or server concern in this design.
- **Model selection is not uniform.** Twelve Python and TypeScript rows read `BOT_PROVIDER`/`BOT_MODEL` through the shared spec. `agent-claude-sdk` reads neither, and `agent-codex` reads only `CODEX_MODEL`. Neither has a `bots` row in `shared/model-providers.json`.
- **Codex is registered but not creatable.** Its registry row is gated (`desktopCreate` and `webCreate` false). Its default port is now 4215, and a Dockerfile and release-manifest entry exist. A local `linux/arm64` image build and `codex --version` passed; the packaged runtime remains unverified. Isolation of shared CLI state, startup service-token visibility, and shell access to the proxy remain unestablished. Re-enabling needs the evidence listed in `decisions.md`.
- **Claude SDK main-mode tool surface is unverified.** A slice that needs a harness with no shell access must check this first. The repo's own tests cover only `/model` mode.
